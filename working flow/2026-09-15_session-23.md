### 2 — Crew 1 architecture (`src/harbor_vale/crews/analyst_crew/`)

- **`runtime.py`** — `Crew1RunContext`: a small, explicit, Crew-1-scoped
  runtime object (paths, raw/clean DataFrames, measured profiles/stats, the
  validated plan objects, the narrative-degradation flag) plus
  `crew1_run_context`/`get_active_context`. **Not Phase 8's
  `PipelineState`.** Chosen over closures for callbacks specifically
  because `Task.callback` is typed `SerializableCallable`
  (`crewai/types/callback.py`) — a closure/bound-method/callable-instance
  all fail `_is_non_roundtrippable` and emit a `UserWarning` (matches
  docs/architecture.md §7's "module-level named functions" rule); using
  the same run-context-lookup pattern for guardrails too (even though
  guardrail closures are fine — `Task.guardrail` is not
  `SerializableCallable`) keeps one uniform, auditable design.
- **`tools.py`** — thin `@tool` wrappers: `profile_dataset`/
  `preview_sample_tool` (Agent 1, run-bound, no path param);
  `get_eda_statistics`/`get_numeric_correlations`/`list_eda_figures`
  (Agent 2, reading the single cached computation Task 1's callback
  produced); `profile_clean_dataset`/`read_insights_report`/
  `read_source_documentation` (Agent 3). No arbitrary-path tool anywhere.
- **`guardrails.py`** — `guardrail_cleaning_plan`, `guardrail_insights_doc`,
  `guardrail_contract_draft`, each wrapping the matching Phase 3/5
  `validate_*` function with the real run context. `GUARDRAIL_MAX_RETRIES
  = 2` is the single constant both the `Task` wiring and the narrative
  attempt-counting logic import.
- **`callbacks.py`** — `execute_cleaning_and_profile`,
  `render_eda_and_insights`, `build_final_contract`: plain, module-level,
  synchronous functions; deterministic only; read exclusively from `ctx`
  (see the CrewAI-behavior findings below for why, not from
  `task_output.pydantic`).
- **`analyst_crew.py`** — `build_analyst_crew` (3 `Agent`s + 3 `Task`s +
  `Process.sequential`, explicit `context=` on every task), `Crew1Result`
  (a local result object, not `PipelineState`), `run_analyst_crew` (the one
  production entry point: builds the context, runs the crew inside
  `crew1_run_context`, catches any exception as
  `status="halted_agent_failure"`, persists the last rejected plan/draft
  under `_internal/` where available).
- **`config/agents.yaml` / `config/tasks.yaml`** — role/goal/backstory and
  task description/expected_output for all three agents; no secrets.

### 3 — Real CrewAI behaviour discovered while wiring (documented in
### `docs/architecture.md`'s new Phase 6 addendum)

Verified empirically against the real pinned `crewai==1.15.20` (scripted
`BaseLLM`, no network — see the addendum for the exact reproduction):

1. A guardrail returning `(True, <bare pydantic model>)` does **not**
   populate `task.output.pydantic` — only a `str` result (re-parsed) or a
   whole `TaskOutput` result does. `task.output.pydantic` is also **not**
   reliably `None` before a guardrail runs on a retry attempt. Production
   rule: never read `task.output.pydantic` in a Harbor & Vale
   callback — every Crew 1 callback reads the validated object from
   `Crew1RunContext` instead, set explicitly by the guardrail.
2. **The narrative-fallback forced-accept mechanism**: on Task 2's final
   exhausted guardrail attempt, `guardrail_insights_doc` returns
   `(True, output)` — the *same* `TaskOutput` it was given, unchanged.
   This hits CrewAI's `isinstance(..., TaskOutput)` branch, which replaces
   `task_output` **without** re-running `output_pydantic` validation —
   proven safe even for a structurally broken final attempt (unlike
   returning the raw string, which WOULD re-validate and could raise).
   Verified end-to-end: crew completes, exactly
   `guardrail_max_retries + 1` guardrail evaluations, Task 3 still runs.
3. A CrewAI `@tool` argument typed with a **named module-level** `Literal`
   alias fails tool-schema construction
   (`PydanticUndefinedAnnotation: '...' is not fully defined`). Crew 1
   avoided the whole class of risk by using a zero-argument, run-bound
   `read_insights_report` tool instead of a single-value-`Literal`-argument
   tool (documented for a future Crew 2 tool that genuinely needs a
   multi-valued `Literal`).

## Architectural Decisions

1. **`Crew1RunContext` + `get_active_context()`, not closures, for
   callbacks; the same pattern reused for guardrails too.** *Why:*
   `Task.callback` is typed `SerializableCallable` and warns on any
   non-module-level callable; keeping guardrails on the identical
   lookup pattern (even though they could be closures) makes the whole
   tool/guardrail/callback surface one uniform, auditable design instead
   of two different idioms.
2. **Callbacks/guardrails never read `task.output.pydantic`.** *Why:*
   empirically proven unreliable in both directions this session (§3
   above) — a genuinely new finding, not assumed from Phase 1/5 docs.
3. **The narrative-fallback forced-accept returns the guardrail's own
   unchanged `TaskOutput` argument, not a string or a synthetic
   placeholder.** *Why:* the only mechanism proven not to re-trigger
   `output_pydantic` validation (and thus not to risk crashing on a
   structurally-broken final attempt) while still letting CrewAI accept
   without raising.
4. **`validate_contract_draft` extended with an optional `clean_columns`
   parameter rather than a new function/schema.** *Why:* the task
   instruction was explicit ("Do not create a second schema"); the
   Phase 5 one-argument-closure-ready pattern already exists for exactly
   this kind of context injection.
5. **EDA figure-column selection is case/underscore-insensitive with a
   measured fallback, not a hardcoded literal match.** *Why:* run 2's real
   live evidence proved a literal match silently produces zero figures
   whenever the agent's own (equally legitimate) renaming choice differs —
   fixed and verified against the real captured data without spending a
   third live run.
6. **Run 2's real, imperfect artifacts (zero figures; empty
   `excluded_features`) are committed as-is, not touched up.** *Why:* they
   are the honest record of what the live acceptance run actually
   produced; synthesizing a "nicer" `eda_report.html` after the fact would
   misrepresent the agent's real output.
