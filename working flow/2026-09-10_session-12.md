## Results

**Task 1.4 — PASS.** `context=[task]` behaviour verified against `1.15.20`.

### API

- **`Task(context=[t1])` exists and works.** Field
  `context: list[Task] | None | _NotSpecified`, **default the sentinel `NOT_SPECIFIED`
  (truthy)**, description *"Other tasks that will have their output used as context for
  this task."* `Task.context` stores the **list of `Task` objects you passed** (task
  references, not outputs); the outputs are read at run time.
- **Implementation path (source-confirmed):**
  1. `Crew._execute_tasks` loop: `context = self._get_context(task, task_outputs)`.
  2. `Crew._get_context`: `if not task.context: return ""` (so `context=[]` /
     `context=None` ⇒ empty). If `task.context is NOT_SPECIFIED` (nothing passed) ⇒
     `aggregate_raw_outputs_from_task_outputs(task_outputs)` — **implicitly ALL prior
     outputs**. If an explicit list ⇒ `aggregate_raw_outputs_from_tasks(task.context)`.
  3. `aggregate_raw_outputs_from_tasks([...])` ⇒
     `[t.output for t in tasks if t.output is not None]` ⇒
     `DIVIDERS.join(o.raw for o in ...)`, **`DIVIDERS = "\n\n----------\n\n"`**.
  4. The string is passed as `context=` to `task.execute_sync` ⇒
     `agent.execute_task(task=self, context=<str>, tools=...)`.
  5. The agent wraps it with the `I18N` `task_with_context` template:
     `"{task}\n\nThis is the context you're working with:\n{context}"`.

### Experiment A — basic context passing (`context=[task1]`)

- Task 1 output reached Task 2: **YES**.
- exact representation: **`TaskOutput.raw`, verbatim** — the literal
  `{"text": "ZZ_MARKER_ALPHA_7f3c9", "count": 11}` appears in Task 2's prompt; no
  wrapper, no re-encoding, no summary.
- exact placement: immediately after `This is the context you're working with:\n`,
  as its own line, followed by `\n\nProvide your complete response:`. The segment
  between the header and the trailer is **only** `t1.output.raw` — no other task text.

### Experiment B — representation for an `output_pydantic` task

- `.raw` used: **YES** — `'{"text": "beta", "count": 22}'` present verbatim.
- `.pydantic` serialized directly: **NO** — the repr `ToyNote(text='beta', count=22)`
  is **not** present.
- `.json_dict`: `None` for an `output_pydantic` task (consistent with Session 9), n/a.
- observed representation: **the raw JSON string the upstream agent emitted**
  (`TaskOutput.raw`). For an `output_pydantic` task that string is valid JSON, so a
  downstream agent *can* parse it — but CrewAI passes it as a **raw string prompt
  injection**, not a typed object.

### Experiment C — callback + context ordering

- event order: `C_t1_llm_call → C_callback_START → C_callback_FINISH → C_t2_llm_call`.
- callback finished before Task 2: **YES**.
- context available to Task 2: **YES** — `C_t1.output.raw` present in Task 2's prompt.
- callback side effect visible: **YES** — the temp file existed with byte-exact body
  when Task 2's agent ran.

### Experiment D — guardrail + context (final output only)

- `D_t1.output.raw` (final) = `'{"text": "ACCEPTED_v2", "count": 9}'` (first attempt
  `count:1` was rejected by the guardrail, retry `count:9` accepted).
- rejected attempt leaked into context: **NO** — `REJECTED_v1` absent from Task 2's
  prompt.
- final accepted output passed: **YES** — `ACCEPTED_v2` present. `context=` reads
  `t1.output`, which is the post-guardrail-loop `TaskOutput`.

### Experiment E — multiple context tasks

- supported: **YES** — `context=[t1, t2]`.
- ordering preserved: **YES** — rendered order == list order. `context=[t1, t2]` ⇒
  `E_ONE_aaa` before `E_TWO_bbb`; `context=[t2, t1]` ⇒ `E_TWO_bbb` before `E_ONE_aaa`.
  Entries joined by `\n\n----------\n\n`.

### Implications for Pattern A (evidence only — decision deferred)

`context=[inspect_task]` / `context=[inspect_task, eda_task]` (§C.2.2) works on
`1.15.20`: the downstream agent **deterministically** receives the upstream task's
**final** `raw` output (post-guardrail, post-callback), in the order listed, under a
fixed header. With Task 1.3 (callback finishes first, artifact flushed to disk), the
full `Agent N → Python callback writes artifact → Agent N+1 (gets prior raw in its
prompt AND can read the fresh artifact via a tool)` chain is demonstrated for the
`Process.sequential` case. Still **not** a decision — Task 1.5 (`Literal` tool
enforcement) remains.

Design notes for Phase 6:
1. **`context=` is `.raw` only — a raw-string prompt injection, not a typed hand-off.**
   The robust channel for a *validated* structure remains: guardrail validates →
   callback writes the artifact → next agent reads it with a scoped read tool. Use
   `context=` for narrative continuity, not as the contract carrier.
2. **The default (no `context=`) implicitly injects every prior task's output.** Crew 1
   tasks should set `context=` **explicitly** (as the Plan pseudocode already does) to
   control exactly what each agent sees.

### Proven vs inferred

- *Proven by execution:* `context=[t1]` passes `t1.output.raw` verbatim into t2's
  prompt under the `task_with_context` header; `.pydantic`/repr is not used; callback
  completes before t2's context is built and consumed; a rejected guardrail attempt does
  not leak (final accepted `raw` is passed); `context=[t1,t2]` renders both in list
  order joined by `\n\n----------\n\n`.
- *Inferred from source only:* the implicit `NOT_SPECIFIED` path (all prior outputs —
  read in `_get_context`, not exercised here); `context=[]` ⇒ `""` (source, not
  exercised); behaviour with `async_execution=True` context tasks (separate `futures`
  path — out of scope).
