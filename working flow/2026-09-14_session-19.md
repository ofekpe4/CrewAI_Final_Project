## Architectural Decisions

1. **Advisory-excluded columns downgrade a missing-column finding from
   ERROR to WARN; hard-excluded columns do not.** *Why:* §F.1's Hebrew
   phrasing ("`excluded_features` עם `enforcement: hard` לא נוכחות → ERROR;
   `advisory` → WARN") is ambiguous out of context; read against §E.4's own
   definition of `hard`/`advisory` (whether the feature may be *used*, not
   whether it may be *absent*), the only self-consistent reading is: a
   missing declared column is ERROR by default (matching
   `validation_policy.on_missing_column`), downgraded to WARN specifically
   when that column is `advisory`-excluded. Verified against the fixture
   contract directly (`total_charges`, advisory) vs. (`customer_id`, hard).
2. **`_dtype_family` treats same-family dtypes as a full pass, not a
   downgraded warning.** *Why:* the Phase 4 prompt explicitly asks for
   "safe conversion / equivalent logical types" to be defined
   deterministically rather than brittle string equality, and pandas
   3.0.5's `str`-vs-`object` reporting (Session 17/18's known issue) is
   exactly the case this exists to absorb — treating it as a WARN would
   itself be a false positive on every text column on this pandas version.
3. **`_MIN_ROWS_FOR_MODELING = 20` and `_MIN_USABLE_FEATURES = 2` are
   documented, chosen constants — the Plan gives no exact figure for
   "sufficient rows"/"≥2 features".** *Why:* matches the same discipline
   `builder.py`'s `_MAX_VALUE_DISTRIBUTION_CARDINALITY` already established
   in Phase 3 — pick once, document why, never infer per-dataset. 20 gives
   the 30-row Phase 3 fixture comfortable margin while still being small
   enough for `truncate_dataset` to trip in a test.
4. **`SCALE_DRIFT_ROW_COUNT` is non-blocking (WARN) even though §F.1 lists
   it under the scale_drift family row.** *Why:* an exact-byte-match
   requirement is already the job of family F (integrity, ERROR); a row-
   count *change* on its own (e.g. the dataset legitimately grew) is not
   evidence of a scale/unit problem — it is informational visibility for a
   human reading the report, consistent with truncation being the thing
   family G (modeling) actually blocks on.
5. **`contract_only_change` also strips `integrity.column_order` and
   refuses referenced columns**, discovered empirically rather than
   designed up front. *Why:* the Plan's own `DatasetContract` cross-field
   validators (Phase 3) are strict enough that a naive "drop one field"
   mutation produces an invalid contract, not the intended "contract
   quietly forgot a column" scenario — the fix keeps the mutated JSON a
   genuinely self-consistent `DatasetContract`, so the fault under test is
   exactly and only the one named.
6. **Family A is the one legitimate prerequisite-gated early exit; B–G
   never stop each other early.** *Why:* explicit in the Phase 4 prompt's
   own decision rule ("the gate runs ALL applicable checks... does NOT stop
   at the first detected error") — the module docstring states this
   boundary explicitly so it is never mistaken for the gate violating its
   own core rule.
