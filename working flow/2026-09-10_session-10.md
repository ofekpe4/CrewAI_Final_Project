## Results

**Task 1.2 — PASS.** Guardrail + retry behaviour verified against `1.15.20`.

### API

- **`Task(guardrail=...)` exists and works.** Type
  `Callable[[TaskOutput | LiteAgentOutput], tuple[bool, Any]] | str | None`, default
  `None`, description *"Function or string description of a guardrail to validate task
  output before proceeding to next task"*. Plural `Task(guardrails=[...])` also exists
  (mutually exclusive with the singular — a non-empty `guardrails` list sets the
  internal `_guardrail` to `None`).
- **Guardrail callable contract** (checked at `Task(...)` construction by
  `validate_guardrail_function`):
  - exactly **one required positional parameter** — else
    `ValueError: "Guardrail function must accept exactly one parameter"`.
  - receives a **`TaskOutput`** instance (attributes `raw`, `pydantic`, `json_dict`,
    `output_format`, …).
  - must return **`tuple[bool, Any]`**; if the return is annotated it must be
    `tuple[bool, X]` with `X ∈ {Any, str, TaskOutput, str | TaskOutput}`.
  - `(True, data)` → success; `data` must not be `None`
    (`Exception("Task guardrail returned None as result. This is not allowed.")`);
    `data` may be a `str` (replaces `raw`, then re-parsed) or a whole `TaskOutput`.
  - `(False, msg)` → failure → retry.
- **Retry fields:**
  - `max_retries: int | None = None` — **DEPRECATED** (*"Use guardrail_max_retries
    instead. Will be removed in v1.0.0"*). If set, `handle_max_retries_deprecation`
    emits a `DeprecationWarning` and copies the value into `guardrail_max_retries`.
  - `guardrail_max_retries: int = 3` — **authoritative**, **default 3**.
  - `retry_count: int = 0` — live counter (reached `1` in Experiment A).
- **Feedback template** (`I18N` `validation_error`):
  `### Previous attempt failed validation: {error}\n\n\n### Previous result:\n{raw}\n\n\nTry again, making sure to address the validation error.`
  It is passed as the `context=` argument to `agent.execute_task` on each retry.

### Experiment A — fail once, then pass (`guardrail_max_retries=2`)

- retry occurred: **YES**.
- guardrail evaluations **2**; agent/LLM calls **2** (1 initial + 1 retry).
- feedback propagated: **YES** — LLM call #0 prompt had no feedback marker; LLM call #1
  (the retry) contained `### Previous attempt failed validation: count must be >= 2 …`.
- final: `crew_output.pydantic == task.output.pydantic == ToyNote(text='good', count=2)`;
  `task.retry_count == 1`.

### Experiment B — never passes (`guardrail_max_retries=2`)

- guardrail evaluations **3** (= `guardrail_max_retries + 1`); agent/LLM calls **3**.
- final failure: a **plain `builtins.Exception`** — *no dedicated guardrail-error
  class* — message
  `"Task failed guardrail validation after 2 retries. Last error: always rejected"`.
- invalid output escaped: **NO** — `crew.kickoff()` raised; `task.output` is `None`.

### Experiment C — retry configuration

- `max_retries`: **still works but deprecated**. `max_retries=1` → `DeprecationWarning`
  *"The 'max_retries' parameter is deprecated and will be removed in CrewAI v1.0.0.
  Please use 'guardrail_max_retries' instead."* → `task.guardrail_max_retries == 1` →
  2 guardrail evals, then `Exception("… after 1 retries")`.
- `guardrail_max_retries`: **exists, authoritative, default 3**. No param → 4 guardrail
  evals, then `Exception("… after 3 retries")`.
- observed rule: **total guardrail evaluations = `guardrail_max_retries + 1`**, and
  **total agent invocations = `guardrail_max_retries + 1`** (initial + N retries).

### Experiment D — guardrail ↔ `output_pydantic` ordering (proven by execution)

For an agent that returns a plain string with a `guardrail` configured:

1. `agent.execute_task()` → raw string.
2. **Pydantic parsing is SKIPPED on the initial pass** when a guardrail is present
   (`_execute_core` only calls `_export_output` in the *no-guardrail* branch).
3. `TaskOutput(raw=<string>, pydantic=None)` is built.
4. **The guardrail runs first**, receiving that `TaskOutput` — `.pydantic is None`,
   `.raw` = the raw string (confirmed in D-A/D-B1/D-B2: `pydantic_is_None: True`).
5. On guardrail **success** returning a `str`: CrewAI then runs `_export_output` →
   **pydantic validation happens *after* the guardrail** → `.pydantic` populated
   (D-A), **or `pydantic.ValidationError` is raised and propagates out of
   `kickoff()`** (D-B1) — the retry loop does **not** catch it.
6. On guardrail **failure**: feedback context built → `agent.execute_task(context=…)`
   again; on each retry `_export_output(new_result)` **does** run inside the loop —
   a valid retry populates `.pydantic` and the guardrail re-runs on it (D-A eval 1:
   `pydantic_is_None: False`); a still-invalid retry raises `pydantic.ValidationError`
   **mid-loop** (D-B3), not the "after N retries" `Exception`.

Recovery:

| case | outcome |
|---|---|
| **Semantic** rejection (guardrail `False` on structurally-valid output), later attempt OK | **recovers** — D-A ends `.pydantic = ToyNote(text='v2', count=9)` |
| **Structural** failure, guardrail **approves** the invalid output | **not recoverable** — `ValidationError` right after guardrail passes (D-B1) |
| **Structural** failure, guardrail **rejects**, a later retry yields valid JSON first | **recovers** — D-B2 ends `.pydantic = ToyNote(text='ok', count=3)` |
| **Structural** failure, guardrail **rejects**, every retry stays invalid | **`pydantic.ValidationError` raised mid-loop** (D-B3) |

**Design implication (for Phase 6 / §C.2.2 / §D.1 / §D.3):** a Harbor & Vale guardrail
must parse `output.raw` itself (it cannot assume `output.pydantic` is set), and should
perform the Pydantic parse *inside* the guardrail and return `(False, msg)` on
structural failure — otherwise a structurally-broken agent output either escapes as a
bare `ValidationError` or is only caught non-deterministically depending on retry
timing, instead of going through the intended retry-with-feedback-then-fail-visibly path.

### Experiment E — PEP 563 gotcha (found while building the spike)

With `from __future__ import annotations` in the module that defines the guardrail, a
guardrail annotated `-> tuple[bool, Any]` has that annotation stored as the *string*
`'tuple[bool, Any]'`; `validate_guardrail_function` then raises
`pydantic.ValidationError: "If return type is annotated, it must be Tuple[bool, Any]"`
at `Task(guardrail=fn)` construction. Real annotation object → accepted; stringized
annotation → rejected. Mitigation: in guardrail modules, either omit the guardrail
return annotation or do not use `from __future__ import annotations`.
