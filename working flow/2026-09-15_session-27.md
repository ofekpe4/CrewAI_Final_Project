### 4 — Live acceptance run 1 — infrastructure halt (not an agent defect)

Ran `scripts/run_crew2.py` against the real, gate-passed Session 26 Crew 1
handoff. The Phase 4 gate passed (0 errors/warnings). Crew 2 started; the
Feature Engineer and Modeling Specialist tasks both succeeded (their
`FeaturePlan`/`ExperimentPlan` guardrails passed). The run then halted
**inside Task 2's deterministic training callback**, not from a guardrail
exhaustion:

```
Input X contains NaN. LogisticRegression does not accept missing values
encoded as NaN natively.
```

Root cause, verified directly: the real `artifacts/crew1/clean_data.csv`
(Session 26's live Crew 1 output) genuinely still carries **11 measured
nulls in `TotalCharges`** — a legitimate fact about that specific run's
Inspector output, not a defect in this session's code. The Feature
Engineer's `FeaturePlan` legitimately included `TotalCharges` (it is a
plain `required_features` entry in this contract, per Session 26's own
documented "Known Issues" note). `ml/features.build_preprocessor` had no
NaN-handling case anywhere: `sklearn.StandardScaler` silently passes a NaN
through by design (it computes `nanmean`/`nanstd` and does not reject NaN
input), and no estimator this project trains accepts one at `.fit()` time.
This is a genuine, previously-unexercised gap in Phase 5's own feature-
building code — no existing Phase 5 fixture ever had a real numeric null
reach the preprocessor, so the gap was never caught by Phase 5's own test
suite.

**This is not a "critical architecture contradiction" requiring a stop.**
It is a normal, scoped implementation bug discovered by the first real
production-data exercise of a code path Phase 5 built but never tested
against real nulls — the same category of finding Phase 6 Sessions 24–26
made and fixed autonomously.

## Architectural Decisions

1. **`read_experiment_results` is wired only onto Agent 6, not Agent 5.**
   PROJECT_PLAN.md §G.2 point 3 lists it as an Agent 5 tool "after
   training," but within this Phase's fixed 3-Agent/3-Task Pattern A (no
   post-training narrative Task), it can only ever return real content
   after Task 2's own callback trains — during Task 2 itself it could only
   raise. The tool exists in `tools.py` for interface completeness; wiring
   it to the one agent that genuinely runs after training (Agent 6)
   satisfies the Plan's intent without inventing a 4th Task. Not a
   contradiction requiring a stop.
2. **The NaN-imputation fix stays inside the SAME single feature path**
   (`_numeric_pipeline`/`_categorical_pipeline` wrapping the existing
   passthrough/transform/encoder branches), not a second path or a
   `FeaturePlan` schema addition. *Why:* the Plan explicitly forbids
   rebuilding Phase 5's feature execution or inventing a second feature
   path; this fix is additive robustness to the one path that already
   exists, discovered only because a real live run exercised real data
   Phase 5's own fixtures never had.
3. **Crew 2's `handoff_status`/`contract_version`/`validation_warnings`
   live as plain `Crew2RunContext` attributes**, populated by
   `scripts/run_crew2.py` (trusted orchestration, which runs the gate
   itself), rather than templated through `kickoff(inputs=...)`. *Why:*
   one explicit, inspectable place — the same reasoning Crew 1's
   `dataset_name` already follows on `Crew1RunContext` — and Crew 2 never
   re-decides the gate's PASS/FAIL either way.
