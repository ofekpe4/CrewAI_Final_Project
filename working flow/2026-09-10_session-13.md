## Results

**Task 1.5 — PASS.** `Literal` tool-arg enforcement verified against `1.15.20`.

### API / mechanism (source-confirmed)

- `@tool` returns `crewai.tools.base_tool.Tool` (a `CrewStructuredTool`). Its
  `.invoke(input)` → `_parse_args(input)` → **`self.args_schema.model_validate(raw)`**
  → **only then** `self.func(**parsed_args)`. On failure:
  `ValueError("Arguments validation failed: <pydantic> …")`.
- `BaseTool` subclass: `.run(**kwargs)` → **`_validate_kwargs`** →
  **`self.args_schema.model_validate(kwargs)`** → **only then** `self._run(**kwargs)`.
  On failure: `ValueError("Tool '<name>' arguments validation failed: <pydantic> …")`.
- Both build `args_schema` from the signature via `pydantic.create_model`, so a
  `Literal[...]` annotation becomes a pydantic `Literal` field.
- Agent-side (`ToolUsage._use`): the raised `ValueError` is caught, `on_tool_error`
  fires, `should_retry = True`, and `self.use(...)` is re-entered — i.e. the agent
  receives the error (with the tool's argument schema, incl. the allowed values) and
  can try again. After `_max_parsing_attempts` it returns a `ToolUsageError` string.

### Experiment D — generated schema (mechanical enum?)

Both `@tool` and `BaseTool` produce the same `resource` field schema:

```json
{"resource": {"enum": ["alpha", "beta"], "title": "Resource", "type": "string"},
 "required": ["resource"]}
```

The allowed `Literal` values appear as a JSON-Schema **`enum`** — a mechanical
allowed-value constraint, not prose.

### Experiment A — VALID call (`resource="alpha"`)

`pick_resource.run(resource="alpha")` → returned `'picked::alpha'`; body call log
`['@tool:alpha']` → **body executed exactly once**, result reaches the caller.

### Experiment B — INVALID call (`resource="gamma"`)

- `@tool`: `builtins.ValueError` — `Tool 'pick_resource' arguments validation failed:
  1 validation error … resource: Input should be 'alpha' or 'beta'
  [type=literal_error, input_value='gamma', …]`.
- `BaseTool`: `builtins.ValueError` — same `literal_error`, schema name
  `PickResourceBaseToolSchema`.
- **body call log empty for both.** **ASSERT: invalid `Literal` rejected BEFORE the
  tool body — TRUE.**

### Experiment C — agent correction

Scripted ReAct agent: attempt 1 `Action Input {"resource": "gamma"}` → validation
fails; the **2nd LLM prompt carried the tool-error feedback**, including
`enum: ["alpha","beta"]` (excerpt: `…Tool pick_resource accepts these inputs: … "enum":
["alpha","beta"] …`); attempt 2 `{"resource": "beta"}` → body runs; `Final Answer`.
Crew completed. Tool body call log: `['@tool:beta']` — **`gamma` never ran the body;
only the corrected `beta` did.** Task completed.

### Experiment E — `@tool` vs `BaseTool`

Both exercised directly (Experiment B ran both). Same generated `enum` schema, same
pre-body `ValueError` on an out-of-set value, same underlying call
(`args_schema.model_validate`). Source confirms one shared mechanism.

### Handoff-allowlist question — explicit answer

Throwaway `read_handoff_probe(name: Literal["clean_data", "dataset_contract"])` (reads
nothing):

- `name="clean_data"` → body ran, returned `'would-read::clean_data'`.
- `name="raw_data"` → `ValueError: Tool 'read_handoff_probe' arguments validation
  failed: … name: Input should be 'clean_data' or 'dataset_contract'
  [type=literal_error, input_value='raw_data', …]`; **body did not run.**

**Answer: YES.** A future `HandoffName = Literal["clean_data", "dataset_contract"]`
would cause `read_handoff("raw_data")` (any value outside the set) to be **rejected by
pydantic before the underlying Python read body executes**, for both `@tool` and
`BaseTool`. This mechanically backs §G.0 layer 1 (logical names, no path parameter).
Note: this covers *value* enforcement; §G.0 layer 2 (the exact-file allowlist /
`../` / symlink defence) is still deterministic Python to be built in Phase 5, not a
CrewAI feature.

### Proven vs inferred

- *Proven by execution:* `Literal` → JSON-Schema `enum`; valid value runs the body once
  and returns; out-of-set value raises `ValueError` (`literal_error`) with the body
  never entering, for both `@tool` and `BaseTool`; the agent receives the error +
  allowed values and corrects; the handoff-style `Literal` rejects a bad name pre-body.
- *Inferred from source only:* the exact `_max_parsing_attempts` count and the final
  `ToolUsageError` wording when an agent never corrects (not driven to exhaustion here);
  `ainvoke`/async tool path (out of scope).
