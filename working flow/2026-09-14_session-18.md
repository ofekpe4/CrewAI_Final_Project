Session 17 concluded CrewAI 1.15.20 requires the *exact legacy spelling*

## Work Completed

- **Isolated runtime verification**, same guardrail body, same
  `Task(description=..., expected_output=..., guardrail=fn,
  guardrail_max_retries=2)` construction, only the return annotation
  varied, each case in its own minimal module (so `from __future__ import
  annotations` — a module-level effect — could be isolated cleanly):
  - **Case A** — `def guardrail(output) -> tuple[bool, Any]:` (PEP 585,
    modern), no future-annotations import → `Task(...)` **constructs
    cleanly**. `guardrail.__annotations__` = `{'return': tuple[bool,
    typing.Any]}` (a real object, not a string).
  - **Case B** — `def guardrail(output) -> Tuple[bool, Any]:`
    (`typing.Tuple`, legacy), no future-annotations import → **constructs
    cleanly**. `__annotations__` = `{'return': typing.Tuple[bool,
    typing.Any]}`.
  - **Case C** — same as Case A, but the module has `from __future__ import
    annotations` → `__annotations__` = `{'return': 'tuple[bool, Any]'}` (a
    **string**) → `Task(...)` **raises**
    `pydantic_core.ValidationError: ... If return type is annotated, it
    must be Tuple[bool, Any]`.
  - **Case D** — `def guardrail(output) -> tuple[bool, object]:` (Session
    17's actual original failing case — `object`, not `Any`), no
    future-annotations import, so a real, non-stringized annotation →
    `__annotations__` = `{'return': tuple[bool, object]}` → `Task(...)`
    **still raises**, the identical `ValidationError`.
- **Conclusion:** Session 17's finding was wrong in its stated generality.
  `tuple[bool, Any]` and `Tuple[bool, Any]` are equally accepted — Python's
  typing system treats the two spellings as equal at runtime, and CrewAI's
  `Task.guardrail` validator accepts both. The real, precise rule has two
  independent parts: (1) the annotation must be a **real, non-stringized**
  object — exactly the Phase 1 Task 1.2 PEP 563 finding
  (`docs/architecture.md` §5), now confirmed to hold for an actual
  `Task(guardrail=...)` construction, not just reasoned about from source;
  (2) the second type argument must be literally `Any`, not `object` (or,
  presumably, any other type — only `object` was tested, since that was
  what Session 17 actually used). Session 17's original failure (Case D's
  shape) was caused by `object` vs. `Any`, **not** by `tuple` vs. `Tuple` —
  a variable Session 17 never isolated.

## Architectural Decisions

1. **Correct in place, with an explicit "CORRECTED in Session 18" marker,
   rather than only appending a new section.** *Why:* `docs/architecture.md`
   and `docs/contract_spec.md` are living reference documents (unlike a
   `working flow/` session record, which is an immutable log entry) —
   leaving a wrong production rule standing, with a correction bolted on
   elsewhere, risks a future phase reading the original (wrong) claim and
   missing the correction. The wrongness and the correct replacement are
   now in the same place, clearly labeled as a correction, with the exact
   evidence that drove it — not silently rewritten as if the mistake never
   happened.
2. **No implementation change.** `validate_contract_draft`'s existing
   `Tuple[bool, Any]` annotation was never actually wrong — it was already
   one of the two annotations proven to work. The corrected understanding
   only removes a false constraint ("must be exactly this spelling"), it
   does not require touching working code.
3. **A dedicated fix branch, not a direct `main` commit.** *Why:* Phase 3
   is already merged to `main`; per the project's Git workflow rules, any
   change — including a documentation correction — goes through the normal
   branch → PR → self-review → merge sequence, even for a small, focused fix.

## Results

The precise, now-verified rule: a Harbor & Vale guardrail's return
annotation must be a **real (non-stringized) object equal to
`Tuple[bool, Any]`** — `tuple[bool, Any]` and `Tuple[bool, Any]` are
interchangeable; a module importing `from __future__ import annotations`
(stringizing the annotation) or using `object` in place of `Any` both break
`Task(guardrail=...)` construction, with the identical
`pydantic_core.ValidationError`. Session 17's "exact legacy spelling
required" claim is retracted; its underlying evidence (the Case-D-shaped
failure) was real, just misattributed to the wrong variable.
