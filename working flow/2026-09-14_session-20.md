### 2 — Validation settings calibration

- **Confirmed via `grep`**: `config/settings.yaml`'s `validation:` block
  (`scale_drift_median_rel_tolerance: 0.25`, `target_positive_rate_tolerance_abs:
  0.05`) is consumed by **zero code** — `config/llm.py` reads only the `llm:`
  block; nothing reads `validation:`. The sole authoritative, enforced
  source of tolerance policy is each `DatasetContract`'s own declared
  per-column `scale_drift`/`target.drift` constraints, read only by
  `contract/validator.py` — confirmed this was already true before this
  session (Phase 4's `_check_scale_drift`/`_check_target` never touch
  `settings.yaml`), so no code change was needed to establish that
  invariant, only to document it clearly as the answer to "which source is
  authoritative."
- **Calibrated, did not fabricate**: `scripts/calibrate_validation_tolerances.py`
  (new, deterministic, `numpy.random.default_rng(42)`) bootstrap-resamples
  the REAL `data/raw/telco_customer_churn.csv` (7,043 rows — not the 30-row
  synthetic fixture) at several batch sizes, 3,000 iterations each, to
  measure how much apparent drift pure sampling noise alone produces — the
  only real-data-grounded evidence available, since this project has no
  actual recurring monthly data feed to measure real drift against (a
  single static Phase 2 download).
- **Result** (full method + tables in new `docs/validation_calibration.md`):
  at the realistic full-population operating scale (this pipeline always
  validates the whole downloaded dataset, not small batches), sampling
  noise alone never exceeded 1.99% for `monthly_charges`' median or 2.12
  percentage points for `churn`'s positive rate, across 3,000 draws. `0.25`
  sits ~12.5× above that noise ceiling (safe, not brittle) and ~400×+ below
  any real incident-scale deviation (×2 error = 100% deviation; the
  mandatory ×100 incident = 9,900%). `0.05` sits ~2.4× above the noise
  ceiling for positive rate — a real but not excessive margin.
- **Decision**: both values **remain 0.25 / 0.05**, status changed from
  "Provisional... calibrated... in Phase 4" to **calibrated/documented**,
  with an explicit pointer to `docs/validation_calibration.md` and an
  explicit statement that these are a suggested default for future Phase 6
  `ContractDraft` authoring, never a runtime-enforced fallback.
- **`config/settings.yaml` updated in place**: the `validation:` block's
  comment now states the calibrated status, points to the evidence doc, and
  states plainly that `contract/validator.py` never reads this block.

## Architectural Decisions

1. **The two new artifact-path parameters are required, not optional with a
   skip-when-omitted default.** *Why:* §F.1 states Family A's four-artifact
   check unconditionally; an optional/skippable design would leave "Family A
   sometimes checks four artifacts, sometimes two" — which does not actually
   resolve the audit finding, it just makes the gap harder to notice. Every
   caller (including every test) must now supply a real answer for all four.
2. **Presence-only for the two narrative artifacts — existence + size, never
   content.** *Why:* explicit in the task; `eda_report.html`/`insights.md`
   are Crew 1 narrative deliverables Crew 2 must never read (§G.0), and
   nothing about Family A's requirement ("קיימים ולא ריקים" — exist and are
   not empty) asks for semantic validation of these two the way the CSV/
   contract pair gets (JSON-parsed, Pydantic-validated). Proven directly by
   two dedicated tests rather than left as an unverified design claim.
3. **`config/settings.yaml`'s tolerances stay non-authoritative — a
   documented default, never wired into `contract/validator.py`.** *Why:*
   introducing a settings.yaml-reading fallback path into the validator
   would create exactly the "two competing sources of truth" this task
   explicitly warned against; the contract-only enforcement model (§E.1
   rule 6) was already Phase 3/4's design, this session only had to confirm
   and document it, not change it.
4. **Calibration evidence comes from the real 7,043-row dataset via
   bootstrap resampling, not an invented number.** *Why:* explicit
   instruction not to fabricate a statistical justification; this project
   has no real recurring data feed to measure actual drift against (one
   static Phase 2 download), so bootstrap noise-floor estimation from the
   real data is the most honest evidence obtainable, and is stated as such
   (not oversold as "real month-over-month drift") in
   `docs/validation_calibration.md` §2.
5. **A dedicated fix branch (`fix/phase-4-family-a-and-calibration`), not a
   direct `main` commit — and `v0.3.0-gate` left untouched.** *Why:* Phase 4
   is already merged (PR #6, commit `26c8d87`) and tagged; per the project's
   Git workflow rules and this session's explicit instruction, a post-merge
   correction goes through the normal branch → PR → self-review → merge
   sequence, and a pushed tag is never silently moved. See **Git Status**.
