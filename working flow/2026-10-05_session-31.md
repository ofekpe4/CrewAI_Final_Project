## Architectural Decisions

1. **Prompt-only correction, confirmed against repository evidence
   first.** The shared `ClosedDomainConstraint` model and the SAME
   rejected draft's own correctly-typed `target.closed_domain.values`
   together prove the schema was never the problem — only the task text
   was silent about a rule the schema already enforced. Changing the
   schema (e.g. accepting `int | bool | str`) would have weakened a
   correct, already-proven contract invariant to paper over an LLM
   formatting lapse; rejected.
2. **No fence-stripping or lenient-JSON preprocessing added to
   `validate_contract_draft`.** Technically would also fix the symptom
   (and is not schema weakening), but the approved scope for this task was
   specifically "ONE narrowly-scoped prompt/output-format correction" —
   adding parser-level leniency is a second, different kind of change not
   asked for, and masks future prompt regressions instead of surfacing
   them as a guardrail retry (which, with the new prompt text, is now
   expected to succeed on the first attempt — confirmed live, §4).
3. **Both new test files extend an existing, established pattern rather
   than introducing a new one.** `test_analyst_crew.py`'s prompt-content
   test mirrors Session 24's precedent exactly (assert the task TEXT
   contains specific guidance, not "the LLM behaves correctly" — a canned
   fixture proves nothing about a real run). `test_plans_validation.py`'s
   three new tests reuse the already-shared `build_draft()` fixture and
   the file's own `test_*`-autodiscovery runner, adding zero new
   infrastructure.
4. **The live run's freshly-regenerated `artifacts/crew1/*` were
   deliberately NOT kept as a new committed baseline**, even though this
   run's Crew 1 output was genuinely valid (not corrupted) — because
   `artifacts/crew2/*` never changed (Crew 2 didn't run), and keeping one
   half of a mismatched Crew1/Crew2 pair would silently invalidate
   README's existing, specific Phase 8 success citations and reintroduce
   the exact hash-mismatch failure mode diagnosed in §3. The PROOF value
   of this live run is captured in this record and in the (git-ignored)
   log file, not in a new committed artifact set.

   crew1/*` internally inconsistent if that run halts mid-way (critical
   agent failure after cleaning/EDA but before the contract step).** This
   is not a new bug introduced this session — it is the direct, visible
   consequence of the pre-existing architecture (`contract/builder.py`
   writes `clean_data.csv`/`eda_report.html`/`insights.md` incrementally

   (`halted_agent_failure`, no fallback — exactly Phase 6's guarantee

   future phase is whether a halted Crew 1 run should also revert its own
   partial writes automatically, rather than leaving the human/next
   session to notice and restore. Documented here rather than silently
   patched, since it is outside this task's approved scope (prompt/
   output-format only).

   `HarborValeFlow().kickoff()` — test or live — rewrites `artifacts/
